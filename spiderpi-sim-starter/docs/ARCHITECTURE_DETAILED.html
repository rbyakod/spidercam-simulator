SpiderPi Simulator Detailed Architecture

This document explains the current SpiderPi Simulator system in detail: repository structure, backend runtime, frontend UI, state model, transport layer, configuration, frame-planning UI, and the path to deploying and evolving the project on a Raspberry Pi for future hardware use. It reflects the current workspace code, including the simulator, the engineering and stadium views, XY map drag control, and the frame planner tab.

1. System Overview

SpiderPi Simulator is a local two-process application that models a Spidercam-style four-cable camera rig. The backend is the authoritative machine-state owner. It computes carriage position, cable lengths, spool movement, and simulated motor step deltas. The frontend is a client that visualizes that state, provides operator controls, and includes planning tools for designing a physical frame. 

Operator UI
  ├─ Simulator tab
  │   ├─ 3D scene (Engineering / Stadium)
  │   ├─ XY map with drag-to-move
  │   ├─ controls panel
  │   └─ telemetry panel
  └─ Frame Planner tab
      ├─ frame geometry inputs
      ├─ drive parameter inputs
      ├─ computed anchors / bounds / cable travel
      └─ engineering preview

Frontend transport hook
  ├─ GET /state polling fallback
  ├─ POST /move, /path, /stop, /estop, /reset-estop
  └─ WebSocket /ws state subscription

FastAPI backend
  ├─ config load
  ├─ shared runtime state
  ├─ motion target and path handling
  ├─ 60 Hz simulation loop
  ├─ 20 Hz state broadcast loop
  └─ geometry-derived cable calculations

Primary Purpose

Provide a visual and interactive simulator for a cable-camera system, with enough geometry and drive math to support planning and future hardware parity.

Current Operating Mode

Simulation only. The project exposes hardware-oriented config fields and a parity plan, but it does not yet drive GPIO, step pulses, or limit switches on real hardware.

3. Backend Architecture

The backend is intentionally compact and centered in backend/main.py. It loads configuration once at startup, exposes REST and WebSocket endpoints, maintains a shared runtime state file, and advances the simulated carriage over time.

Framework

FastAPI provides routing and WebSocket support. Uvicorn runs the ASGI app. Pydantic validates request payloads and configuration data.

Persistence Strategy

Configuration is persisted in YAML. Runtime simulator state is persisted to a JSON file and protected with lock files so dev reload mode does not split machine state across processes.

Startup Load config, derive anchors/bounds/spool parameters, ensure runtime files exist, acquire leader lock, start sim loop and push loop.
Motion Model Point-to-point constant-speed movement toward target in XYZ. Cable lengths and step counts are derived from geometry on each tick.
State Broadcast Current state is pushed to WebSocket clients roughly 20 times per second.
Safety Model Current safety is limited to bounds clamping and E-stop latching. There is not yet any cable tension, collision, or physical feasibility model.

Backend functions and what they do

Function / Object Location Purpose
Manager backend/main.py Tracks connected WebSocket clients and broadcasts serialized state payloads.
lengths_from_xyz() backend/main.py Computes Euclidean cable length from each anchor to the carriage position.
steps_from_delta_length() backend/main.py Converts cable length change into motor steps using spool circumference, motor steps/rev, and microstepping.
default_state() backend/main.py Creates the initial machine state, including current position, bounds, anchors, lengths, and empty trail/path data.
with_state_lock() backend/main.py Central state accessor that loads runtime JSON, applies mutations, and writes it back under an exclusive lock.
set_target() backend/main.py Clamps target values to configured bounds and marks the machine as moving.
advance_state() backend/main.py Main sim tick function. Advances toward target, updates cable lengths, spools, steps, timestamps, and trail.
sim_loop() backend/main.py Runs at ~60 Hz and advances the simulation continuously.
push_loop() backend/main.py Runs at ~20 Hz and publishes the latest state to all WebSocket subscribers.
square_path(), circle_path() backend/planner.py Create sampled waypoint lists used for canned motion demos.

4. Frontend Architecture

The frontend is a single React application built with Vite. It is intentionally lightweight and renders almost directly from the backend state contract. It now has two top-level tabs: Simulator and Frame Planner.

Simulator Tab

Contains the 3D scene, the live controls, the XY map, and telemetry. It is the operator-facing runtime view.

Frame Planner Tab

Provides a design-time UI for entering frame dimensions and seeing derived anchors, bounds, cable lengths, spool turns, and steps.

Current frontend components

Component Purpose Current behavior
App.tsx Layout shell Owns tab state, scene mode, lighting mode, sidebar collapse, sidebar resize, and overall page composition.
useSpiderSocket.ts Transport and command API Fetches current state, opens WebSocket, polls every 250 ms as fallback, and posts move/path/stop/E-stop commands over HTTP.
SpiderScene.tsx 3D visualization Supports Engineering and Stadium scene modes, top/side/front camera presets, lighting modes, and renders the carriage plus cables and towers.
TopMap.tsx 2D XY interaction Renders the current XY position and lets the user drag the camera marker to issue bounded X/Y moves while holding Z constant.
Controls.tsx Command panel Provides jog buttons, path buttons, stop, E-stop, and reset E-stop.
Telemetry.tsx State readout Shows connection status, current XYZ, motion state, and cable lengths A-D.
FramePlanner.tsx Design tool Calculates anchors, bounds, workspace, cable travel, steps, turns, warnings, and previews for a user-specified frame.
The frontend currently targets http://127.0.0.1:8000 and ws://127.0.0.1:8000/ws directly in useSpiderSocket.ts. This is fine for local development, but it should eventually move to environment variables for Raspberry Pi deployment and cross-device access.

5. Runtime State Model

The backend publishes one main state object. The frontend TypeScript shape is defined in frontend/src/types.ts. This schema is effectively the contract between backend and frontend.

Field Type Meaning
modestringCurrent machine mode. Today this is simulator-oriented and not yet a full parity state machine.
statusstringidle, moving, or stopped in current runtime.
estopbooleanEmergency-stop latch flag.
position{x,y,z}Current carriage pose in simulator coordinate space.
target{x,y,z}Current active target position.
speednumberCurrent move speed in meters per second equivalent.
anchorsanchor mapAnchor coordinates loaded from config and rebroadcast to clients.
boundsXYZ rangesClamped simulator workspace for motion targets.
lengthsmapCurrent cable lengths for A/B/C/D.
stepsmapAccumulated motor-step deltas per cable.
spoolsmapAccumulated spool rotation proxy derived from cable travel.
trailarrayRecent carriage positions used for visual trails.
pathobjectActive path name, current index, and sampled points.
updated_attimestampLatest state-write time.
The current state model is enough for simulation, but it is not yet the full hardware parity state machine described in docs/HARDWARE_PARITY_PLAN.md. Fields such as controller_ready, faults, and calibration_valid are not yet present.

6. Configuration Model

Configuration is defined in backend/persistent_config.py and persisted to backend/data/spiderpi.yaml. It is already structured for future hardware use even though only part of it is consumed by the current simulation loop.

FrameConfig

Defines anchor coordinates, workspace bounds, spool radius, and motor steps/rev.

RigConfig

Contains carriage mass, payload mass, gravity, drag coefficient, speed limit, and acceleration limit.

MotorTuning

Electrical and motion-drive values such as current, torque, DRV8825 Vref, microsteps, and step frequency limits.

CalibrationState

Placeholder for homing status, zero lengths, offsets, spool calibration, direction validation, and notes.

In the current runtime, the simulator directly uses frame.anchors, frame.bounds, frame.spool_radius_m, frame.motor_steps_per_rev, and motors.microsteps. The rest of the config is modeled but not yet enforced by runtime logic.

7. Frame Planner UI

The Frame Planner is a non-destructive design calculator. It is meant to help choose physical frame dimensions for a DIY build and immediately see the geometry-driven consequences in terms of anchors, workspace, cable travel, spool turns, and motor steps.

Planner inputs

  • Frame width and frame length
  • Anchor height
  • X and Y edge margins
  • Minimum and maximum working Z
  • Spool radius
  • Motor steps per revolution
  • Microsteps
  • Carriage mass and payload mass
  • Target max speed and max acceleration

Planner outputs

  • Recommended anchors A/B/C/D
  • Recommended simulator bounds x/y/z
  • Usable workspace dimensions
  • Frame diagonal
  • Steps per meter
  • Turns per meter
  • Cable length range
  • Per-corner cable travel and approximate steps
  • Sample point lengths and worst cable angle
  • Geometry warnings for obviously awkward frame choices
This planner is already valuable for real-world build sizing because it uses the same geometric length formula that the simulator uses for cable calculations.
It is still a planning tool, not a physical feasibility solver. It does not yet calculate tension, sag, torque reserve, or live hardware current limits.

8. Runtime Flows

Flow A: Startup

  1. Backend loads YAML config.
  2. Backend loads or initializes runtime state JSON.
  3. Backend starts a shared simulation loop and a shared push loop.
  4. Frontend loads.
  5. Frontend fetches GET /state.
  6. Frontend opens WebSocket /ws.
  7. UI renders from the latest state object.

Flow B: Point move

  1. User clicks a jog button or drags the XY map marker.
  2. Frontend posts /move with {x, y, z, speed}.
  3. Backend clamps target to bounds and marks status moving.
  4. Simulation loop advances toward target each tick.
  5. Cable lengths, step counts, spool values, and trail update continuously.
  6. Frontend re-renders from polling and WebSocket updates.

Flow C: Path execution

  1. User clicks Square or Circle.
  2. Backend generates sampled waypoints with planner.py.
  3. Current target becomes the first waypoint.
  4. When the carriage nears a point, backend advances to the next one.
  5. When the list is exhausted, status returns to idle.

Flow D: E-stop

  1. User triggers /estop.
  2. Backend sets estop = true and status = stopped.
  3. Simulation loop no longer advances state.
  4. User must call /reset-estop before motion commands resume normal effect.

10. Raspberry Pi Deployment Path

The current codebase can already run on a Raspberry Pi as a simulator and UI host. To turn it into a stable Pi-based platform, the first deployment should separate two concerns:

  • Run the simulator and UI reliably on the Pi
  • Later replace the simulated execution layer with real motor control

Recommended Raspberry Pi role

Phase 1: Pi as simulator host

Run FastAPI and the frontend on the Pi. Use a browser locally or from another device on the same network to operate the system.

Phase 2: Pi as machine controller

Add hardware controller modules that generate step pulses, read limit switches, and enforce startup safety before live movement.

Suggested Raspberry Pi software setup

  1. Install Raspberry Pi OS Lite or Desktop on a Pi 4 or Pi 5.
  2. Install Python 3, Node.js, npm, and git.
  3. Clone the repository into a writable home directory.
  4. Create a Python virtual environment for the backend.
  5. Install backend dependencies from requirements.txt.
  6. Install frontend dependencies with npm install.
  7. Use npm run build and serve static assets, or run the Vite dev server during development.

Recommended production arrangement on Pi

  • Run the backend as a systemd service under a dedicated user.
  • Serve the frontend as built static files via Nginx, Caddy, or a simple file server.
  • Proxy API and WebSocket traffic from a stable hostname or IP to the backend process.
  • Replace hardcoded 127.0.0.1 URLs with environment-based configuration before multi-device access.

Minimal systemd service concept

[Unit]
Description=SpiderPi Backend
After=network.target

[Service]
WorkingDirectory=/home/pi/spiderpi-sim-starter/backend
ExecStart=/home/pi/spiderpi-sim-starter/backend/.venv/bin/uvicorn main:app --host 0.0.0.0 --port 8000
Restart=always
User=pi

[Install]
WantedBy=multi-user.target
Before exposing the UI across the network from a Pi, change the frontend transport hook so API and WebSocket URLs come from environment variables or relative paths. The current hardcoded localhost URLs are development-only.

11. Future Hardware Integration

The repository is now organized around the idea of future hardware parity, but live hardware control is not implemented yet. The correct next step is not to bolt GPIO calls directly into the current simulation loop. Instead, the runtime should evolve toward the architecture described in docs/HARDWARE_PARITY_PLAN.md.

What will be needed before real hardware motion

  • Explicit controller modes such as sim, dry_run, and hardware
  • A stricter machine state model with readiness, faults, homing, and calibration validity
  • A hardware controller abstraction layer separate from the sim controller
  • Homing routines and limit-switch handling
  • Real step generation for motors and enable/disable control
  • Environment-based endpoint configuration for the frontend
  • Engineering-view-only geometry for debugging live machines

Likely Raspberry Pi hardware responsibilities later

Responsibility Current status Future Pi role
Step pulse generation Not implemented Drive A/B/C/D motor channels using GPIO or a dedicated motion driver board.
Direction and enable control Only modeled in config Set DIR and EN pins per corner motor driver.
Limit switch reads Only modeled in config Use GPIO inputs to support homing and travel verification.
Calibration storage Modeled in YAML Persist zero lengths, offsets, and validation results after commissioning.
Safety interlock Software E-stop only Eventually combine software E-stop with physical emergency-stop circuitry.
Do not interpret the current simulator as ready for unattended live movement on a Raspberry Pi. It can help size the frame and prototype behavior, but it is missing the runtime guarantees and control abstractions required for real motors.

12. Current Limits and Risks

  • The motion model is constant-speed interpolation in XYZ, not a cable-space hardware execution loop.
  • There is no real collision model, no tension model, and no cable sag model.
  • There are no automated tests in the repository.
  • The frontend still uses hardcoded backend URLs.
  • The simulator uses one shared spool radius in runtime math even though future parity work intends to move to per-corner spool modeling.
  • The runtime contract is still simpler than the intended parity state machine.
  • The current E-stop is software-only.
  • The frame planner computes useful geometry and drive conversions, but not physical feasibility under load.
Even with those limits, the project is already useful for four things: simulator interaction, cable-length sanity checks, frame sizing, and preparing the system structure for later Raspberry Pi-based hardware control.
